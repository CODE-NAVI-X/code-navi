# 产品路线图

## 产品定位

Code Navi（智教码航）是面向计算机专业学习与项目实践的通用代码学习助手。用户围绕当前任务自然提问；应用根据上下文按需组合学习、练习、项目辅助、信息检索、代码测试和仓库能力，不要求用户通过内部能力名交互，也不强制依次完成固定模块。

产品使用仓库内置且保持独立边界的 `kernel` 运行单 Agent，把业务提示、任务状态、Skill/Workflow、工具权限和人工确认保留在 `code_navi` 应用层。

## 当前基线

截至 2026-07-18，以下仓库级能力已经完成：

- Code Navi 应用层与 kernel 的代码边界已经拆分，并在同一仓库内可复现交付；
- 通用代码学习 Agent 默认不具备工具权限；
- CLI 支持单次问题和进程内问题分支；
- 项目 README、可选任务摘要、显式文件片段和上一条回答可以组成受限 ContextSlice；
- 默认 Mock 和显式 OpenAI Provider 都经 `AgentRuntime` 接入；
- 每个问题生成独立 run 和可定位的 Event JSONL；
- 原三个领域 Agent 暂时保留兼容导出。

当前基线不是完整产品，也不代表真实模型服务、GUI、持久化对话、代码执行、Skill 系统、OpenMAIC、远程仓库或多 Agent 能力已经上线。

## P1：任务空间与能力契约

目标：让未来 GUI、CLI 和独立模块围绕同一个任务状态与能力协议协作。

计划范围：

- Task Workspace 及可持久化任务、约束、产物和待确认问题；
- `AssistantTurn`、`ActionProposal` 和用户确认协议；
- Tool、Skill、Workflow 的统一 manifest 与版本；
- 需求补全 Skill 和可确认的 RequirementBrief；
- CLI 只展示用户动作，不暴露内部能力名。

验收：需求补全可独立调用；任务状态可暂停恢复；模型提议不能绕过能力注册、参数校验和权限确认。

### P1 增量：对话式科研澄清与动态研究画像

科研澄清在应用层 SQLite 保存动态 `ResearchProfile` 与完整消息，不再要求用户按固定顺序填写五个字段。显式配置 Provider 时，无工具权限的科研对话 Agent 经公开 `AgentRuntime` 产生严格校验的画像 patch、候选问题和下一问；成熟度、写入、会话恢复和搜索权限由应用规则控制。超时、网络失败、无 Key 或输出不合法时使用确定性规则继续，不中断或丢失会话。

学生端 `/research` 已迁移到版本化 `/api/v1/research/conversations`：支持自然多轮消息、建议选项、候选问题、科研画像、可解释成熟度、处理摘要、刷新恢复、具体错误和移动端折叠布局。浏览器只保存 `conversation_id`，不保存密钥或模型响应副本。旧五字段 `/sessions` 暂时作为 API 兼容层保留，不再由新页面调用。

受限学术检索已经接入新对话主流程：查询词由结构化画像确定性生成，用户检查查询和来源后显式执行；OpenAlex、Crossref 与 arXiv 在 allow-list 内并行查询，部分失败时保留成功结果。EvidenceBundle 记录来源状态、耗时、访问时间和 `fact/inference/to_verify` 边界，并在 SQLite 持久化和按会话复用 TTL 缓存。涉及联网时仍必须通过显式注册并授权的 `READ + NETWORK` Tool。

当前增量不自动联网、不接入 MCP、不下载正文或生成论文证据卡，也不把处理摘要冒充内部思维链。下一科研阶段可评估论文去重增强、可选全文获取与证据卡，但必须先定义版权、访问权限、引用定位和人工核验边界。

## P2：学习与信息来源

目标：支持轻量即时讲解和结构化学习内容，同时保持来源边界。

计划范围：

- 技术资料、项目资料和学术来源的检索 Skill；
- 带来源、访问时间和待核验项的 EvidenceBundle；
- OpenMAIC 作为外部学习内容服务的版本固定适配器；
- GUI 微窗口所需 LearningThread 数据契约；
- 学习结果按用户选择回写主任务，而非自动污染项目上下文。

## P3：受控代码运行与练习

目标：通过独立沙箱服务支持编译、运行、可见测试和教学反馈。

进入条件：明确沙箱隔离、资源限制、网络策略、隐私清理、并发限流和许可证结论。Agent 不得直接在宿主机执行用户代码或获得无限制 shell。

首批范围以 Python、可见测试和结构化错误为限；隐藏测试、正式判题和多语言在安全验收后独立扩展。

## P4：项目 Workflow 与仓库接入

目标：支持课程项目和科研项目的需求补全、任务拆分、实施记录和成果整理。

GitHub 接入先支持检查与绑定已有仓库，再增加创建和首次推送。认证、远程创建、remote 修改和 push 都需要独立确认、审计、幂等和部分失败处理。

## P5：产品化与扩展验证

在前述契约稳定后，再评估身份权限、GUI 部署、更多 Provider、长期会话、质量评估和跨角色协作。多 Agent、自动评分、自动发布和不经复核的科研结论必须独立立项。

## 路线图规则

- 每一阶段只有通过书面验收后才能标记完成。
- 范围变化必须同步更新架构、不变量、非目标和测试计划。
- 涉及高风险外部操作时，先定义确认、审计和回滚，再实现功能。
- 路线图描述计划，不替代 issue、设计文档或 PR 中的具体实现证据。
