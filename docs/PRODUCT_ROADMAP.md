# 产品路线图

## 产品定位

智教码航面向计算机专业人才培养，覆盖助学、助教、助研。产品以可复用的单 Agent 运行时为底座，使三个方向能够在各自的业务边界内定义 Agent、接入受控工具并保留运行审计信息。

这一定位不表示完整业务、Web、真实模型在线运行或多 Agent 课堂已经完成。当前路线首先交付可验证的内核与领域接入，再逐步建设应用闭环。

## 四层架构

| 层 | 职责 | 当前边界 |
| --- | --- | --- |
| `core` | 平台无关的类型、单 Agent 执行循环、工具注册与权限、上下文策略、Event 语义。 | 不放业务提示、教学策略、平台 SDK、界面或多 Agent 编排。 |
| `runtime` | 将 `AgentSpec`、`RuntimeRequest`、Provider、dispatcher、配置和单次运行组合为 `AgentRuntime`。 | 业务方只经此层调用，不直接进入 `core` 循环。 |
| `domain` | 助学、助教、助研的 Agent 声明、业务提示、输出约定与获准工具清单。 | 现有目录为 `domains/student/`、`domains/teacher/`、`domains/research/`。 |
| `app` | 未来的命令入口、服务编排、身份与数据接入、人工确认、展示和业务流程。 | P0 未建设为完整应用；该层不得把平台细节反向放入 `core`。 |

数据和控制流遵循：`app` 选择一个 `domain` Agent，调用 `runtime`，由 `runtime` 驱动 `core`；Event 作为一次运行的审计事实返回给 `app`。反向依赖和绕过 `runtime` 的调用不纳入路线。

## 三组分工

| 小组 | 负责内容 | 不负责内容 |
| --- | --- | --- |
| 助学组 | `domains/student/` 中的学生辅导 Agent、学习输入与可检查的学习输出。 | 修改内核循环、权限语义或替用户自动完成高风险操作。 |
| 助教组 | `domains/teacher/` 中的教师助理 Agent、教学材料草案、评价建议与人工复核入口需求。 | 在内核中实现课程规则、直接发布教学结论或构建未验收的 Web。 |
| 助研组 | `domains/research/` 中的科研辅导 Agent、证据边界、研究计划与不确定性标注。 | 编造实验结果、将未核验资料当作结论或修改 Provider/循环契约。 |
| 运行时维护者 | `kernel/core/` 与 `kernel/runtime/` 的稳定契约、回归测试和审计工具。 | 为单一领域需求把业务规则写进内核。 |

跨组共享的改动应先判断属于领域层还是应用层；只有影响所有宿主的稳定执行语义，才由运行时维护者按内核契约评审。

## 阶段计划

### P0：可复用内核与领域接线

目标是让三组都能以同一运行时契约完成一次可审计的单 Agent 运行。

范围包括：

- `AgentRuntime`、`AgentSpec`、`RuntimeRequest` 的单次运行接入；
- 三个领域目录中的最小 Agent 声明：助学、助教、助研；
- 显式工具注册、按 `AgentSpec.tool_names` 精确选择、每 run 独立授权与 dispatcher；
- Event-only JSONL 输出及 `python -m kernel.trace <path>` 追踪；
- 使用 `MockProvider` 的离线接线验证。

P0 不宣称已经完成完整业务、Web、真实模型在线服务或多 Agent 课堂。

#### P0 验收

- 三组各有至少一个可导入的 `AgentSpec`，且名称、描述、系统提示均非空；其职责分别对应助学、助教、助研。
- 三组均可通过 `AgentRuntime.run(agent, RuntimeRequest(...))` 用 `MockProvider` 完成一次单 Agent 运行，并获得 `RuntimeResult` 中的输出与 Event。
- 无工具 Agent 在没有 `dispatcher_factory` 时可运行；声明工具的 Agent 在没有工厂时应被拒绝。
- 有工具的接入只暴露 `AgentSpec.tool_names` 声明的工具，顺序一致；每次运行创建新的 `PermissionGrant` 与绑定 dispatcher。
- 设置 `session_dir` 后，单次运行的 JSONL 路径符合 `<session_dir>/<session_id>/<run_id>.jsonl` 或 `<session_dir>/<run_id>.jsonl`，并可由 trace 命令读取。
- 三组接入不修改 `kernel/core`，不直接调用 `kernel.core.run()`，不将 JSONL 误作跨 run 会话恢复。

### P1：三组最小业务闭环

P1 在应用层为每组建立一个可人工复核的最小流程；以下是建议，不表示已经实现。

| 小组 | 最小闭环建议 | 人工复核点 |
| --- | --- | --- |
| 助学 | 输入学习目标、题目或代码片段；输出分步提示、下一步练习和自检条件。 | 教师或助教确认题目范围、答案边界和学习建议。 |
| 助教 | 输入教学目标、作业要求或评分规则；输出教学活动草案、题目草案或评分提示。 | 教师确认内容准确性、课程进度和最终发布。 |
| 助研 | 输入研究问题与已有证据；输出研究计划、待验证假设、证据缺口和待补资料。 | 研究者确认来源、方法可行性与任何结论。 |

共同约束：仍只通过 `AgentRuntime` 调用；业务逻辑留在 `domain` 或 `app`；工具显式注册且最小授权；工具结果、模型输出和人工决定应可用 Event 关联；没有证据时明确标记不确定性；不得把单 Agent 流程包装成已完成的多 Agent 课堂。

### P2：受控数据与评估扩展

在 P1 闭环经过人工验证后，逐项增加受控资料源、领域工具、输入输出质量评估和运行失败处理。写入或破坏性操作必须保留每 run 授权、工作区边界和人工确认。每个新增工具、数据源或评价指标都应有独立的失败标准与回归测试。

P2 仍不因接入数据而默认拥有通用 Web 产品、跨平台消息集成或自动化教学决策；这些能力需要在应用层另行立项和验收。

### P3：产品化与扩展验证

在 P0--P2 的契约保持稳定并获得实际使用反馈后，评估应用入口、身份与权限治理、部署、更多 Provider 适配、运行观测和跨角色协作。每项扩展须证明不会破坏单 Agent 的 Event、工具授权和领域边界。

多 Agent 协作、课堂自动化和真实在线 Provider 的持续运行均属于待评估的扩展项，不是本路线图对当前完成状态的声明。

## 长期共同约束

- `core` 保持平台无关；领域提示、业务策略、界面和 Provider SDK 不进入该层。
- 一次 JSONL 文件只记录一个运行；`session_id` 只组织目录，不能恢复跨运行的对话或权限。
- 工具采用显式注册和最小授权；权限与绑定 dispatcher 均按 run 新建，不跨运行继承。
- 任何面向学生、教师或研究者的输出都应区分事实、工具返回、推断和待核验项。
- 每个阶段只宣称已通过相应验收的能力；未完成的业务、Web、在线模型和多 Agent 课堂必须明确标为后续工作。
